# Claude Code

- Claude Code moves fast and its docs change under you. Before modifying anything Claude Code related (settings, rules, skills, plugins, marketplaces), and before answering a question about Claude Code, the Agent SDK, or the Claude API, consult the `claude-code-guide` agent: it reads the live docs, and `find-docs` (Context7) lags weekly releases. A page named by a skill, a rule, a memory, or the user is a primary source: fetch it directly. A URL recalled from training data is not
- **Rules record decisions, not documentation**: when writing a rule file or CLAUDE.md entry, each line must state a preference or contract — never how an external tool behaves (that rots when the tool changes, and find-docs covers it) and never a quoted vendor string or version-specific identifier. Where a checked-in file already encodes the decision, cite it as the authority instead of restating its content.
- **Published claude.ai system prompts are a per-model-defaults signal only**: the pages at https://platform.claude.com/docs/en/release-notes/system-prompts/claude-fable-5-1 and https://platform.claude.com/docs/en/release-notes/system-prompts/claude-opus-5 show what Anthropic itself has to tell each model, so a behavior a page spells out is not that model's default. They apply to claude.ai, not to the API or Claude Code, so they never settle whether Claude Code's own prompt already carries a line.
- **Claude Code behavior archaeology**: for "when did prompt, flag, or env var X change", use https://github.com/marckrenn/claude-code-changelog, which extracts each release's system prompts, `tengu_*` feature flags, and CLI surface; its tag-to-tag compare shows when something appeared or died. Rejected as a pointer in `audit-claude-settings`: it tracks no settings keys, its env-var list is latest-release only while `strings` on the installed binary is version-matched ground truth, and its changelog text is the first-party file.
- **Skill `model:` is turn-scoped, not skill-scoped**: an inline skill's `model:` override applies for the rest of the turn that invokes it, so composing such a skill mid-turn downgrades everything after it. Set `model:` only on `context: fork` skills or skills that always own the whole turn. For dispatcher skills, pass `model` per Agent call instead. Inside a `context: fork` skill the fork's own `model:` wins for every turn: an inline skill it invokes keeps its `model:` pin only on paper.
- **Skill `context: fork` caveats**: a fork gets no conversation history, so the body must open with an "invoking this skill IS the request" paragraph and take its input via args, quoting `$ARGUMENTS` on its own line rather than substituting it mid-sentence, where a sonnet fork read the substituted value as a placeholder name (`skills/pr/SKILL.md` is the authority). Backgrounded forks run a narrower tool set (Agent may be missing, set `background: false` if needed), skill frontmatter hooks don't fire, and background-fork edits are outside `/rewind` checkpoints.
- **Keep the hal-skills `skills` array in both manifests**: `skills/.claude-plugin/plugin.json` and the `hal-skills` entry in `.claude-plugin/marketplace.json` list the same skill paths on purpose. The first is what Claude Code reads for the plugin's own metadata; the second is what `npx skills` reads to group them. Dropping either copy silently loses one of the two, so keep them in sync instead of deduplicating. A skill directory added to or removed from `skills/` has to be added to or removed from both arrays; the `publish-plugins` skill checks that with `scripts/check_manifest_sync.py`.
- **Hook matchers exclude `AskUserQuestion` from `PermissionRequest`**: `AskUserQuestion` fires `PreToolUse` and `PermissionRequest` back to back, so a `PermissionRequest` hook that treats every tool alike double-fires on a question. Negative lookahead in the `matcher` (a JavaScript regex) is the fix; `plugins/hal-voice/hooks/hooks.json` is the authority.
- **Hook config is snapshotted at session start**: an edit to a plugin's `hooks.json`, including a hand-patched copy under `~/.claude/plugins/cache/`, changes nothing until `/reload-plugins` or a restart. Reload before trusting a hook test.
- **Testing local skill or plugin changes**: start the session with `claude --plugin-dir /usr/local/hal-9000/skills --plugin-dir /usr/local/hal-9000/plugins`; the checkout overrides the installed copies for that session, forks included. After each edit run `/reload-plugins`. No version bump, reinstall, marketplace swap, or restart. Never swap the `hal-9000` marketplace to the local directory instead: each `marketplace add` and reinstall rewrites `dotfiles/.claude/settings.json` through the symlink, and `plugin update` skips an unchanged version.
